| Cache Chez FFI symbol lookups across calls (per-call dlsym dominates wall on tensor-heavy workloads) | perf | M | **Confirmed dominant bottleneck for Llama-3.2-1B inference on torch-mps F32 (2026-05-27).** Sample profile (`/usr/bin/sample <pid>`) of a 44-min-in HfLlamaInference run shows 100% of CPU time in `S_foreign_entry → lookup → dyld4::Loader::hasExportedSymbol`, recursively walking every loaded library (libtorch contributes thousands of symbols on top of libidrisml). Every `%foreign` call into the C library re-resolves the symbol via dyld instead of using a cached pointer. **Root cause** (per `feedback_typeclass_zero_arg_method_eval.md` + the `tensor lifecycle` wrapped-handle ABI): `%foreign "scheme:EXPR"` wraps EXPR inside `(lambda (farg-0) (EXPR farg-0))` — the lambda body is re-evaluated on every call. The generated Scheme code from `scripts/lifecycle/ffi-convert-to-scheme.py` puts the `(foreign-procedure "C-name" ...)` call inside that lambda body, so each call constructs a fresh foreign-procedure object → fresh dlsym. **Fix direction**: rewrite the Scheme template so each `%foreign` binding evaluates `(foreign-procedure ...)` exactly once at module load and the per-call lambda captures the cached procedure via let-binding: `(let ([fp (foreign-procedure "C-name" ...)]) (lambda (a b c) (fp (unwrap a) ...)))`. Touchpoints: `scripts/lifecycle/ffi_manifest.py` (the manifest generator) + `scripts/lifecycle/ffi-convert-to-scheme.py` (the template), with `make check-ffi-wrap-template` updated to enforce the new shape. Cross-references: existing Medium-priority "Idris-side per-op overhead" row that listed this as suspect (6) of a broader investigation — this row promotes the suspect to a confirmed fix-level entry, since Llama-scale (16 layers × multi-head attention + MLP × 1.24B params) makes the dispatch wall painfully visible. **Why high priority**: actively blocks practical use of HfLlamaInference (44+ min for a single forward at 31% CPU, almost all of it dlsym), and same root cause hurts every tensor-heavy workload (transformer / NTM / DNC / gpt-full) to a lesser but still meaningful degree. Catches the high-stakes drift class (NTM/DNC dimension changes, GPT vocab/seq-len, controller widths). **(B) Layer-graph drift** — harder. Idris-side encodes architecture as a model expression like `linearLayerAny {i=4} {o=128} ~~> tanhLayerAny ~~> OutputLayer linearLayerAny {i=128} {o=2}`; PyTorch-side encodes it in `nn.Module.__init__` + `forward`. Needs an AST normalisation step on both sides producing a comparable layer graph (a flat list of `(LayerKind, args)` tuples), then a diff. Idris-side parsing benefits from the `~~>` / `OutputLayer` shape being structured; Python-side needs walking `__init__` for `nn.X(...)` assignments plus the `forward` method for the operation order. The `forwardVarTraced` infrastructure on the Idris side already produces a layer-by-layer trace at runtime — might be a cheaper path than static parsing if we accept "run both sides, compare traces". Out-of-scope intentional divergences (paired-side init differences documented in `reference-alignment.md`; mlx-only f32 cast etc.) need per-example overrides like the hyperparameter checker has. Deliverable: `scripts/check-paired-arch.py` + `make check-paired-arch` + CI gate (after deduping with `check-paired-defaults`). Saves the same class of mid-PR confusion the hyperparameter checker saves, one architecture-shaped layer up |
| Bound resource usage (memory + handle count) | feature | M | Two unbounded resources today, both observable but neither capped: **(1) Memory** — tape-backend arena (the chunked allocator in `backend_tape/arena.c`) grows linearly with example complexity and epoch count; torch carries an `intermediates` vector; mlx's MTLBuffer pool grows in lockstep. A long-running training can OOM with no upper bound. Observability: add `prim__memUsed` / `prim__memPeak` and surface them in `runTraining`'s logEpoch line alongside RSS (RSS is already there). Enforcement: a `--memory-limit` CLI flag (or env `IDRIS_ML_MEM_LIMIT`) that aborts the run with a clear error when arena + persistent param footprint exceeds the limit, instead of letting the OS kill the process. Tape's chunked arena makes the check cheap — each new chunk request can compare the running total. Likely also wire to mlx's `mx::set_memory_limit`. **(2) Handle count** — live Tensor handle counts (`tensor_live_count` / `tensor_peak_live_count`, already surfaced in the logEpoch `handles=` field and the timing-summary `Live handles` / `Peak handles` lines) also grow without bound when something leaks. Observability is done; enforcement isn't — a `--handle-limit` flag (or env) that aborts on threshold-cross catches the bug class "forgot to free per-sequence state tensor" instantly, before the run lopes for hours and dies. Same shape as the memory cap: cheap counter, abort path, surfaced in the per-epoch line. Useful both for CI hygiene and for catching unintentional state leaks. Cross-references: `backend_tape/arena.c` (chunked allocator), `tensor_live_count` (lifecycle counter), `docs/develop/tensor-lifecycle.md`. |
